# G-SAVE 当前状态与后续工作

更新时间：2026-08-17

本文用于跨设备继续开发，记录聊天中已经确定但不能只依赖聊天上下文保存的决定、当前
实现状态、验证结果和下一步工作。长期架构硬约束仍以仓库根目录的 `AGENTS.md` 为准。

## 1. 当前产品方向

G-SAVE 是 Windows 优先、基于 Git 的游戏存档管理工具。Core 是无窗口、事件驱动的
极简被动触发器；GUI 仅按需运行。游戏未运行是常态，空闲时不得初始化 libgit2、Lua、
网络 SDK，不得创建常驻 Worker、线程池、日志、托盘或 IPC 服务。

存档目录本身就是 Git 工作区和仓库根目录：不使用影子仓库、不复制第二份常驻存档、
不分发 `git.exe`。提交和推送发生时才创建临时线程，任务结束后立即回收。

## 2. 支持包与路径配置的最终规则

支持包导入和游戏配置是两件事：

1. “导入支持包 ZIP”只校验并安装包文件，让支持包卡片出现在列表中。它不运行
   `install()`、不初始化 Git、不写主 TOML。
2. 点击专用支持包卡片后，由支持包的 `install(context)` 自动定位游戏 EXE、进程名和
   全部存档目录。GUI 展示检测结果并让用户确认，但不要求也不允许用户选择路径。
3. 专用包检测失败时显示明确原因，例如未安装游戏、Steam 库未找到、尚未生成存档；
   停止配置并让用户修正环境后重新检测，不回退到手动路径选择。
4. 只有没有专用支持包的游戏使用“添加其他游戏”通用流程，玩家才需要手动选择游戏
   EXE 和存档目录。通用方案只提供时间戳和通用文件元数据。
5. 已安装的支持包始终显示卡片；再次点击已配置卡片就是重新自动检测并更新配置，
   同时保留原有启用状态和云端同步策略。

多数游戏存档位于 `%APPDATA%`、`%LOCALAPPDATA%`、Documents/My Games 或 Steam
`userdata/<账号>/<AppID>`。路径根只是宿主 API；每个专用包仍必须声明 AppID、相对路径、
文件名或 glob，并校验实际存档文件，不能让 GUI 对整个用户目录做盲目递归扫描。

当前四个专用包的自动检测目标：

| 游戏 | 自动检测的存档根目录 |
|---|---|
| DARK SOULS III | `%APPDATA%\DarkSoulsIII` |
| ELDEN RING | `%APPDATA%\EldenRing` |
| DRAGON'S DOGMA: DARK ARISEN | `Steam\userdata\<账号>\367500\remote` |
| DRAGON'S DOGMA 2 | `Steam\userdata\<账号>\2054970\remote\win64_save` |

## 3. 当前代码与尚未完成的界面修正

支持包 ZIP 导入与配置已经分离，导入后卡片会保留；通用包仍可手动配置。专用包 Lua
已经可以通过受限宿主 API 查询 Known Folder、Steam 安装库和 Steam userdata。

但源码中的 `GuiController::installManifest()` 目前仍保留旧行为：专用包自动检测失败后
会打开“选择游戏程序”和“选择游戏存档文件夹”，检测成功对话框也提供“手动选择”。
这与第 2 节的最终规则冲突，是换设备后应先完成的修正。

相关文件：

- `src/gui/gui_controller.cpp`
- `qml/pages/GamesPage.qml`
- `packages/*/adapter.lua`
- `docs/游戏支持包使用指南.md`
- `docs/新游戏支持包制作教程.md`
- `README.md`

建议的最小改法：专用包检测结果完整时直接进入一次确认；结果缺少 EXE 或仓库时汇总
`problems` 并报错返回；仅 `package.generic == true` 时打开两个路径选择器。同步删除界面、
Lua 错误信息和使用文档中的“专用包可手动选择/修正路径”文案。不要新增向导、路径状态
机或扫描服务。

## 4. 已完成的主要功能

- C++23 Core，Windows 事件驱动进程与目录监听，共享 IOCP。
- 原地 Git 仓库、初始基线、安静期/周期/退出提交、提交失败有限重试。
- Git Remote 推送、网络错误有限重试，本地历史独立于网络成功。
- Qt 6 Quick/QML GUI：支持包、时间线、恢复、完整时间线分歧处理、Core 启停与自启。
- GitHub、Gitee、GitLab、Gitea 服务识别；服务地址 + Token 的玩家配置流程。
- Token 保存到 Windows Credential Manager，不写入 TOML。
- 云端设置默认作用于全部已配置游戏；新游戏默认在退出游戏后上传。
- 支持包 ZIP 导入兼容正斜杠和 PowerShell ZIP 中的反斜杠条目。
- 应用图标已经嵌入 Core 和 GUI。

WebDAV 和 OneDrive 仍明确延期，不应在当前 Git Remote 流程未稳定前提前实现。

## 6. 性能问题与验证结论

曾经出现几十 MiB 存档提交耗时 154 至 216 秒。根因不是 Git 正常吞吐，而是临时任务
线程使用了 `THREAD_MODE_BACKGROUND_BEGIN`，Windows 同时把磁盘 I/O 和内存优先级
降到极低，造成严重节流。现已改为仅使用 `THREAD_PRIORITY_BELOW_NORMAL` 降低 CPU
优先级，保持正常 I/O 优先级。

修复后的 Release 真实存档回归（初始基线、两轮单字节变化、两次固定 1 秒安静期）：

- DDDA：约 2.4 秒。
- DD2：约 3.2 秒。
- ELDEN RING：约 4.7 秒。

这些数字只代表当前测试机器。不得恢复 `THREAD_MODE_BACKGROUND_BEGIN`，也不得用简单
放宽测试超时掩盖提交卡死或极端节流。

## 9. 换设备后的建议顺序

1. 克隆主仓库并完整阅读 `AGENTS.md` 和本文。
2. 安装 C++23、CMake/Ninja、Qt 6；原开发机 Qt 位于 `D:\Dev\Qt6`，新设备路径可不同。
3. 先实现第 3 节的专用包自动检测流程修正，并更新相应测试和玩家文档。
4. 运行 GUI/模型/包测试和 Release 构建，手工验证四个包的卡片流程：导入 ZIP 只出现
   卡片；点击专用卡片自动检测；失败只报原因；“添加其他游戏”才出现路径选择器。
5. 再安排多仓库真实提交与云端推送测试；不要在游戏运行环境中加入常驻诊断设施。
